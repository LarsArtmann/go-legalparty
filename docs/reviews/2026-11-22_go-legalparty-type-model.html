01Problem catalog

Brutal-honesty pass, graded by severity and systemicity. Green badges mark what this audit fixed and pinned.

Critical · fixed systemic: rule methods

The two class rules disagreed on invalid input

legalform.go:74 (AllowsLEI) · fixed + pinned by TestLegalFormRules

AllowsLEI answered true for any string that was not natural_person — including garbage and the zero value — while RequiresRegistryAnchor answered false for the same input. An invalid class could claim LEI eligibility while being denied a registry anchor: two invariants, one input, contradictory verdicts.

Fix shipped: AllowsLEI now returns c.IsValid() && c != LegalFormNaturalPerson. An invalid class allows nothing, mirroring its sibling rule.

Critical · fixed single type

NL VAT was looser than its own error message

identifiers.go:287 (validateNLVAT) · fixed + 2 new vectors

The rejection message promises "9 digits, B, 2 digits", but the check only verified length 12 and a B at index 9 — NLA23456789B01 passed. A validator more permissive than its documentation is a contract lie in the direction that matters: it accepts malformed billing data.

Fix shipped: the digit positions are now verified (isAllDigits on both sides of the B).

High · fixed systemic: 5 sites

Character-class logic duplicated across five rune loops

identifiers.go:143-179 (isAllDigits / isAllUpperAlpha / isAllUpperAlphaNumeric)

"Is this all digits / uppercase letters / alphanumerics" was hand-rolled in ParseLEI, ParseNIP (twice), validateTaxNumberBody, isPrefixedVATShape, and ParseCountryCode. Five copies of one predicate is five places to disagree on edge input.

Fix shipped: three named predicates, single-homed; all five sites route through them; behavior verified by the existing vectors.

Medium · open systemic: all branded types

Branded strings are constructible without validation

every type X string; invariants enforced only inside Parse*

VATID("garbage") compiles, and the zero value "" is representable for every type. This is the standard Go trade-off for string value objects — making raw construction a compile error would require opaque structs and cost serialization ergonomics the fleet relies on (JSON round-tripping as plain strings).

Verdict: accepted design, not a defect. The Parse functions are the boundary; the honest gap is that callers holding an already-typed value have no uniform way to re-check it — see the next finding.

Medium · open systemic: 4 of 7 types

Validity surface is asymmetric

country.go:303 (CountryCode.IsValid) · legalform.go:44 (LegalFormClass.IsValid) exist; LEI/VATID/TaxNumber/NIP have none

Two types answer "is this value well-formed" with a method; four force the caller to call Parse* and discard the result. Worse, TaxNumber validity is jurisdiction-relative (DE wants 10–13 digits, others 5–16), so a parameterless IsValid() would be a name that lies — it needs IsValidFor(cc).

Recommendation: add IsValid() to LEI/VATID/NIP and IsValidFor(CountryCode) to TaxNumber. Staged as migration M1 below; also the top deepening candidate (docs/architecture-understanding/2026-11-22_19-10_value-library-deepening.html).

Watch · accepted single type

PL VATIDs are length-checked only

identifiers.go:298 (validateFixedLengthVAT)

ParseVATID("PL1234567890") verifies shape, not the NIP checksum — while ParseNIP("1234567890") verifies both. The asymmetry is documented (FEATURES.md, ROADMAP.md) and demand-gated. Recorded here so a future reviewer does not "fix" it without the regulatory pass and consumer-test updates AGENTS.md requires.

02The vision

Perfection for this model is boring, and that is the point: every identifier parses through one verb, every typed value can answer whether it is well-formed through one idiom, every rejection path carries a pinned machine code, and no invariant is enforced in more than one place. After this audit's fixes, the only missing piece is the uniform validity surface (M1).

What the model must never become No pointer fields, no option structs, no separate "draft"/"validated" lifecycle states on the value types — the CQRS aggregate in cqrs-htmx/legalparty-model owns lifecycle; this library owns types, parsing, checksums, nothing else (AGENTS.md scope boundary).

03Go data model

The shape as it stands after the audit's fixes, with the proposed M1 surface in the second block.

// Branded strings: distinct types, plain JSON, Parse as the gate.
type LEI string            // ISO 17442, mod-97 == 1
type VATID string          // canonical EU-prefixed form
type TaxNumber string      // no country prefix, ever
type NIP string            // bare 10 digits, weights 657234567
type CountryCode string    // assigned ISO 3166-1 alpha-2 only
type LegalFormClass string // five peers, closed set

// The one struct: Registry stays opaque by design.
type RegisterRef struct {
    Registry string `json:"registry"`
    Number   string `json:"number"`
}
// M1 (proposed): one validity idiom per type. TaxNumber is
// jurisdiction-relative, so its method says so in its name.
func (l LEI) IsValid() bool
func (v VATID) IsValid() bool
func (n NIP) IsValid() bool
func (t TaxNumber) IsValidFor(cc CountryCode) bool

// Each implementation is exactly Parse-and-discard, so the
// predicates can never drift from the parsers they mirror.

06Decision log

Decision Alternative rejected Why
Branded strings, not opaque structs Struct wrappers with private fields Plain JSON round-tripping; the fleet aliases these types across repos
RegisterRef.Registry is a plain string A Registry branded type with known codes The domain never inspects registry semantics — the resolver owns them (DOMAIN_LANGUAGE.md anti-language)
LegalFormClass as string enum with IsValid iota ints The literal values ("legal_entity", ...) are persisted and cross-repo; integer codes would need a mapping layer
AllowsLEI denies invalid classes (this audit) Keep c != natural_person Two rules must not disagree on the same input; deny-on-unknown matches RequiresRegistryAnchor
TaxNumber validity is jurisdiction-relative Parameterless IsValid A parameterless check could only enforce the generic 5–16 shape and would lie for DE

07Anti-patterns to avoid here

Do not merge VATID and TaxNumber

The conflation is the cautionary tale that motivated this library: one type for both rejects valid values on both sides.

Do not "fix" the NIP remainder-10 edge

Mapping remainder 10 to check digit 0 is the bug class this library exists to prevent. The edge is regulation, not an oversight.

Do not validate inside getters on every call

Parse is the gate; per-access re-validation would hide cost in hot paths and blur where the contract lives. M1's IsValid is explicit and caller-initiated.

Do not add pointer-optional fields to RegisterRef

Optional registry or number would smuggle "state" into a value pair whose whole job is to be complete or rejected.

08Migration roadmap

Add IsValid to LEI/VATID/NIP, IsValidFor(cc) to TaxNumber, with vectors. Awaited only because it is the deepening brief's candidate — the design is settled.

2

3

Weights 8-9-2-3-4-5-6-7 mod 11, remainder 10 → check digit 0 (the opposite edge from NIP). Then delete company-master-data's local copy.

4

ParseNIP/ParseVATID/ParseLEI/ParseTaxNumber/ParseTaxNumberBody; fleet pattern is go-error-family's 16 targets. Tracked in TODO_LIST (Medium).

09Conclusion

The model in one sentence Seven branded types whose types are the fleet's vocabulary, whose parsers are the only gate, whose rejection codes never lie — and after today, whose rules cannot disagree about input they do not understand.
