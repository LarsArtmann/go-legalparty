1 · Give every identifier one validity surface

identifiers.go (LEI, RegisterRef) · vatid.go (VATID) · taxnumber.go (TaxNumber) · nip.go (NIP)
Today: two idioms
CountryCode.IsValid · LegalFormClass.IsValid
LEI / VATID / TaxNumber / NIP → parse, discard the value, keep the error
Callers holding a typed value must re-parse to ask "is this well-formed?" — and the zero value has no uniform answer.
Deepened: one idiom
LEI.IsValid · VATID.IsValid · NIP.IsValid · TaxNumber.IsValidFor(cc)
Every implementation is Parse-and-discard inside, so the predicates cannot drift from the parsers they mirror.

Problem. The interface teaches two validity idioms, and four of seven types leave callers to invent the parse-discard dance — leverage is fine for parsing, thin for re-checking.

Solution. Add the four methods; each is a thin wrapper over its parser, adding behavior without a second implementation to maintain.

  • One idiom, seven types
  • Zero-value checks uniform
  • Interface grows, locality keeps
  • No new dependency
Deletion test Delete the four methods and the re-check complexity reappears in every consumer that holds a typed value — the module is earning its keep; this deepening widens its interface only where callers already are.
