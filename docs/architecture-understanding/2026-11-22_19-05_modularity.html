00Summary

go-legalparty is a single flat package with seven exported value types, one dependency (go-error-family), and zero infrastructure. On the assessment rubric it averages 4.3 / 5 — the Good band, one step from Excellent. Nothing here argues for restructuring: the module boundary, the file-per-concept layout, and the all-public surface are deliberate, documented decisions (ADR-0001, AGENTS.md) that this review confirms rather than relitigates.

The bottom line Maintain and document. The only finding that can hurt consumers is not structural at all: two public parse surfaces still have zero test vectors, so their frozen rejection codes are unpinned. That work is already tracked in TODO_LIST.md.

◆What's already excellent

Five structural assets worth naming, because they are the reason the scores are high.

+
Deep parse interfaces Each Parse* function is a one-call interface over regulation-heavy implementations: weights, seeds, mod-97 arithmetic, normalization (see the deepening brief, same directory). Callers learn one verb per identifier family.
+
Frozen machine-code error contract Every rejection is a stable legalparty.<subject>.<cause> code via go-error-family; tests pin exact codes with the errorCode helper. Dashboards and consumer switches can rely on them.
+
Regulation edges encoded, not assumed NIP remainder-10-invalid, DE ISO 7064 seed-5, LEI mod-97 == 1, assigned-only country table — each carries its regulatory provenance in the code and pinned vectors (MoF, BMF, live GLEIF records).
+
Dependency direction is exemplary Domain depends on stdlib plus one fleet-standard error library; no IO, no framework, no persistence — the scope boundary in AGENTS.md is enforced by the import graph itself.
+
Normalization single-homed The fleet-wide convention (uppercase, trim, strip four separators) lives in one function, normalizeTaxIdentifier (identifiers.go:124), and every parser routes through it. Fix once, fixed everywhere.

01Findings

Ordered by impact. Two were found and fixed during this review session; they are recorded for the audit trail.

Important · Medium impact

Two public surfaces carry zero test vectors

taxnumber.go:16 (ParseTaxNumber) · identifiers.go:94 (NewRegisterRef) · identifiers.go:108 (RegisterRef.Validate)

The error contract is frozen public API, but codes tax_number.required / vat_shape / national_invalid and register.registry_required / number_required have no pinning vectors. Any refactor can silently move a rejection path that no test watches — for a library whose whole point is contract stability, that is the largest remaining risk.

Fix Add table-driven vectors per the AGENTS.md testing pattern (one wantCode per rejection path, DE 10–13 bounds included). Already tracked as the High-Impact row in TODO_LIST.md; effort S.
Nice to have · Low impact

identifiers.go is the jurisdiction-growth hotspot — by design, but watch the gate

identifiers.go (308 / 350 file-size gate lines)

VATID national-part dispatch, the DE checksum kernel, LEI, RegisterRef, and the shared normalization/character kernels all live in one file. That is cohesion, not a god module — but every future jurisdiction checksum (FR, IT, ES; demand-gated in ROADMAP.md) lands here. The 350-line buildflow gate is the tripwire.

Fix Land each new jurisdiction as its own per-concept file (the taxnumber.go extraction on 2026-11-22 is the template). The gate then stays green by construction instead of by trimming.
Nice to have · Fixed this session

Rule methods disagreed on invalid classes; NL VAT was looser than its own message

legalform.go:74 (AllowsLEI) · identifiers.go:287 (validateNLVAT)

Found during this review, fixed and pinned the same session: AllowsLEI answered true for values that never passed ParseLegalFormClass while RequiresRegistryAnchor answered false for the same input; and ParseVATID accepted Dutch national parts with letters in the nine digit positions (e.g. NLA23456789B01) despite its message promising 9 digits, B, 2 digits. Both now deny/enforce exactly what their documentation says — TestLegalFormRules and two new VATID vectors pin the behavior.
